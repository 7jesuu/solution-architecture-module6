BIAN (Banking Industry Architecture Network) используется как:
- общий язык после слияния;
- способ определить границы владения данными;
- инструмент поиска пересечений между FinUnion и RetailBank;
- основа для целевых доменов данных и data products.

| Сущность | Близкая область / Service Domain BIAN | Зачем это нужно |
|----------|---------------------------------------|-----------------|
| **Клиент** | Party Data Management / Customer Management | Единый подход к идентификации и жизненному циклу клиента. Позволяет назначить владельца домена «Party» и построить MDM. |
| **Договор** | Agreement / Product Agreement | Унификация модели договора между розницей и МСБ. Чёткие границы: кто владеет условиями договора. |
| **Продукт** | Product Directory / Product Design | Создание единого продуктового каталога. Устранение дублирования кодов продуктов. |
| **Счёт** | Current Account / Deposit Account | Унификация модели счёта. Определение, какая Core-система является мастером для какого типа счёта в переходный период. |
| **Карта** | Card Management / Payment Card | Выделение карточного домена. Понимание, что статусы и события карт должны быть приведены к единой модели. |
| **Кредит** | Loan / Credit Facility | Унификация кредитных продуктов и графиков. Важно для риск-менеджмента и регуляторной отчётности. |
| **Транзакция** | Payment Execution / Account Transaction | Единые правила фиксации операций. Основа для антифрода и финансовой отчётности. |
| **Платёж** | Payment Order / Payment Execution | Разделение «инициирование» и «исполнение». Помогает правильно построить потоки между CRM и Core. |
| **Обращение** | Customer Contact / Case Management | Единый 360°-профиль. Владелец домена — контактный центр + CRM. |
| **Справочник** | Reference Data Management | Критически важный домен. Без него невозможно стабильное слияние. Должен быть централизован в MDM. |
| **Организация** | Party Data Management (Legal Entity) | Расширение модели Party на юрлиц. Нужно для МСБ. |
| **Событие / Документ** | Document Management / Event Log | Обеспечение lineage и аудита. Поддержка регуляторных требований к хранению. |

## Как BIAN помогает на практике

1. **Унификация терминологии**  
   После слияния «клиент», «договор», «счёт» в FinUnion и RetailBank означают немного разное. BIAN даёт канонические определения.

2. **Границы владения данными**  
   Каждый Service Domain имеет чёткого бизнес-владельца. Это основа для Data Ownership и data products.

3. **Поиск пересечений**  
   Сопоставление As-Is систем с BIAN-доменами сразу показывает, где два банка дублируют функциональность (CRM, Loans, Cards, DWH).

4. **Целевые домены данных**  
   На основе BIAN формируются целевые data domains:
   - Party Domain
   - Product & Agreement Domain
   - Account & Transaction Domain
   - Card Domain
   - Credit Domain
   - Customer Interaction Domain
   - Reference Data Domain

5. **Data Products**  
   Каждый домен в дальнейшем публикует data products (например, `Customer 360`, `Account Balance History`, `Active Loans Portfolio`), которые потребляются BI, рисками, КЦ и цифровыми каналами.
