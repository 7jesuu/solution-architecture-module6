# 3. DWH и Data Lakehouse — детальное сравнение и выбор

## Сравнение для кейса FinUnion + RetailBank

| Аспект | DWH на PostgreSQL | Data Lakehouse (Iceberg + Trino) |
|--------|-------------------|----------------------------------|
| Хранение истории двух банков | Дорого и неудобно | Дешёвое объектное хранилище + таблицы Iceberg |
| Сырые события (карточные операции, клики, логи) | Плохо подходит | Отлично подходит (Bronze → Silver → Gold) |
| Регламентированная отчётность | Отлично | Хорошо (через Gold-слой или витрины) |
| Схема и контракты | Жёсткая, предсказуемая | Гибкая + schema evolution |
| ACID и time-travel | Есть | Есть (Iceberg) |
| SQL-доступ | Нативный | Trino / Spark SQL |
| Сложность эксплуатации | Низкая | Средняя / высокая |
| Стоимость хранения больших объёмов | Высокая | Низкая |
| Поддержка ML и data science | Ограниченная | Хорошая |

## Выбранный подход

| Состояние | Решение | Почему |
|-----------|---------|--------|
| **3 месяца** | DWH на PostgreSQL (+ минимальный landing в объектном хранилище) | Быстрый запуск единой управленческой отчётности, знакомый стек, низкий риск |
| **12 месяцев** | Гибрид: DWH (регламент) + Lakehouse (история, события, ad-hoc, ML) | Нужно хранить объединённую историю двух банков, события и документы без взрывного роста стоимости |

## Роль Apache Iceberg и Trino

- **Apache Iceberg** — табличный формат поверх объектного хранилища. Даёт ACID, time-travel, schema evolution, partition evolution. Позволяет строить надёжный Lakehouse.
- **Trino** — федеративный SQL-движок. Позволяет запрашивать данные из Lakehouse, DWH и даже Operational реплик одним SQL. Снижает необходимость копировать данные только ради объединения.

## Что остаётся в DWH, что уходит в Lakehouse

| Тип данных | Где хранится | Почему |
|------------|--------------|--------|
| Регламентированные витрины (регулятор, управленческая отчётность) | **DWH** | Жёсткие SLA, аудит, согласованность, привычные инструменты |
| Текущие остатки, актуальные срезы клиентов/счетов | **DWH** (+ MDM) | Нужна высокая согласованность и предсказуемая производительность |
| Полная история транзакций и карточных операций | **Lakehouse** (Silver/Gold) | Большой объём, нужна дешёвая история |
| Сырые CDC-потоки и события каналов | **Lakehouse** (Bronze) | Сырые данные, полуструктурированные |
| Архивные выгрузки RetailBank | **Lakehouse** + Object Storage | Разовые большие объёмы |
| Документы, сканы, неструктурированные файлы | **Object Storage** (метаданные в Lakehouse/DataHub) | Классическое объектное хранение |
| ML-фичи и обучающие выборки | **Lakehouse** | Удобно для data science |

## Ограничения выбранного гибридного подхода

1. Нужно поддерживать **два контура** (DWH и Lakehouse) и чётко определять, какой источник является каноническим для какого потребителя.
2. Требуются компетенции по Iceberg, Trino и оркестрации.
3. Без жёсткого Data Catalog и ownership легко получить «два источника правды».
4. Стоимость платформы выше, чем у чистого PostgreSQL DWH, но значительно ниже, чем у попытки уместить всю историю в классический DWH.
